Context

After the Graduate Showcase project wrapped, I moved onto UAL's Design System team for the remaining two and a half months of my contract.

UAL's design system covered eight colleges and multiple digital products, the main website, the Graduate Showcase, Arts Temps. It was fully integrated with the codebase and broadly followed across products. By most standards, it was in good shape.

The brief was straightforward: audit the existing system, identify gaps, recommend updates.

A small team of three: a Design Lead and two contractors, myself included.

The Audit

What we did

We started by building a complete picture of the existing system. The work was systematic: we screenshotted every page across UAL's product suite — homepage, college pages, course pages, subject pages, event listings — and compared each one against the existing design system.

For every element we found, we asked two questions: does this follow the system, or has it drifted? And if it's new, should it be added?

I was responsible for specific components — Promote Card, Notification, Footer — as well as a cross-product H1 sizing audit, checking typography consistency across every page type at 1440px.

What we found

The system itself was largely sound. Most pages followed the spec. Deviations were either minor frontend inconsistencies or intentional additions that hadn't yet been documented.

Two components needed to be added as genuine new additions: a new Promote Card size introduced in the Graduate Showcase, and the updated Filter structure — both outputs of the website project I'd just completed. The work I'd done on the Showcase fed directly back into the system.

Finding the Real Problem

The audit confirmed the components were fine. So I moved on to the next part of the brief: organising and documenting what we'd found.

I started with Promote Card — my responsibility. I laid out the component, its variants, its states. It looked complete. But working through it, something felt off.

What I'd produced was a display. Here's the component. Here's what it looks like. But there was nothing to tell a designer when to use it, how to use it correctly, or what accessibility considerations applied. If someone new joined the team tomorrow and opened this file, they'd see the component — but they wouldn't know what to do with it.

My judgment

This wasn't a problem with my component. It was a structural problem across the entire system. The documentation had been built to show what existed. It hadn't been built to help people use it.

I looked at how mature design systems document themselves — Jira, and a few others. The pattern that works consistently: every component has three layers — Overview, Usage, Accessibility. Not just "here it is" but "here's what it's for, here's how to use it, here's what to watch out for."

I wrote a detailed proposal for restructuring the entire documentation using this framework and presented it to Stephanie. She approved it in the same meeting.

Why this matters

Nobody asked me to look at the documentation structure. The brief was to audit components. But the real friction for anyone using this system wasn't missing components — it was that the system had become hard to use as a reference. A component library that designers can't navigate efficiently is a component library that doesn't get used.

Identifying that was a judgment call, not a task completion.

What Got Built

My contract ended before the full restructure was complete. But the team's Figma workspace remained accessible — UAL's design environment was open.

When I checked back later, the structure had been implemented in full — exactly as proposed.

What the system looked like after

The restructured system covered: UI Toolkit Layout, Design Foundations (Grids, Spacing, Colours, Typography), Molecules (Accordions, Alerts, Buttons, Cards), Organisms (Navigation, Header), and Templates (Homepage, College pages, Course pages).

Each component documented with the three-layer framework. A process flowchart defined how new components would be added going forward — flagged by UI designers, authorised by the Design System Manager, reviewed before merge. The system now had a governance model, not just a component library.

The connection back to the Showcase

The two new components added during this project — the Promote Card size and the Filter structure — both came directly from the Graduate Showcase work. Design decisions made in one project fed back into the shared system that served all of UAL's digital products. That's what a design system is supposed to do.
